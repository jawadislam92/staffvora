# Staffvora - Security & Scale Audit Findings (adversarially verified)

Generated from a 5-dimension audit; each finding independently re-verified by a second reviewer. 61 confirmed, 1 refuted. Owner's standing requirements: must survive 500 orgs / very large companies, and must not be abusable.

## HIGH (27)

### [high-1] Screenshot rate limit is keyed on the client's own captured_at, so a tampered agent bypasses it entirely and can backdate evidence
- **Category:** abuse | **File:** app/Http/Controllers/Api/Desktop/ScreenshotController.php | **Line:** 25, 42-54
- **Impact:** `captured_at` is validated only as `['required','date']` (UploadScreenshotRequest.php:15) and `BusinessTime::fromClient()` (app/Support/BusinessTime.php:104-115) does zero clamping — it accepts any instant from year 1 to year 9999. The per-hour cap therefore counts rows in *the attacker's chosen hour*. Incrementing `captured_at` by one hour per upload makes the counter read 0 forever, so the plan entitlement `max_screenshots_per_hour` and the workspace's own `screenshots_per_hour` setting are both unenforceable — the only remaining brake is the generic 60 req/min API limiter (RouteServiceProvider.php:30). One agent can push ~86k images/day at up to 8 MB each into the tenant's S3 bucket: unbounded storage cost the operator eats, and directory paths (`screenshots/{user}/{Y-m-d}/{session}`, line 59-64) fan out across fabricated dates. It also lets a user *plant* screenshots on days they did not work — the surveillance record itself becomes forgeable, which is the evidentiary artifact an enterprise customer would rely on in a dispute.
- **Fix:** The proposed fix is directionally right but wrong in three specifics and incomplete in three more.

WRONG:
1. Do not add a `received_at` column — `tracking_screenshots` already has `$table->timestamps()` (migration line 33), so `created_at` IS the server-observed receipt time. Count against it: `->where('user_id', $user->id)->where('created_at', '>=', now()->subHour())->count()`.
2. That count has NO supporting index. The only indexes are `['user_id','captured_at']` and `['tracking_session_id','captured_at']`. At 100–500 orgs × 100+ users × months of rows this becomes a scan of every row for that user. Add `index(['user_id','created_at'])` in the same change, or the fix trades an abuse bug for a latency bug on the hottest write path.
3. Do not reach for "Redis/cache counter" as written — the shipped config is `CACHE_DRIVER=file` (.env:21). A file-store counter is not atomic across FPM workers and will undercount under exactly the concurrency you are defending against. Either provision a real atomic cache store first, or use the indexed DB count above (correct and cheap once indexed).

INCOMPLETE — the fix must not stop at ScreenshotController:
4. Clamp inside `BusinessTime::fromClient()` itself (or add `fromClientBounded($iso, $min, $max)`) and apply it at EVERY call site, because the same unclamped helper feeds `SessionController.php:56` (`started_at`), `:147` (`last_heartbeat_at`), `:160` (`stopped_at`) and `ActivityController.php:27` (activity samples' `captured_at`). Reject (422) anything outside `[$session->started_at − small clock skew, now() + ~2 min]`; for session start, bound to `now() ± skew`. Clamping screenshots alone still lets a user manufacture the fabricated workday.
5. Fix retention independently: change `PruneTrackingScreenshots.php:29` to prune on `created_at` (or `LEAST(captured_at, created_at)`), otherwise every already-planted far-future row survives the clamp fix forever. Also run a one-off audit for existing rows where `captured_at > created_at + interval` before launch.
6. Move `GenerateScreenshotThumbnail` off `sync` (config/queue.php:16, .env:23) before launch, or the upload path keeps doing image resizes inside the web worker regardless of the quota fix.

On the dedicated route throttle: yes, add one at `routes/api.php:60-62`, but make it materially tighter than the shared 60/min (a legitimate agent at, say, 12 shots/hour needs nowhere near that), and apply the same treatment to `/activity/batch` at `:63-65`, which shares the identical unclamped-timestamp and shared-bucket profile.

### [high-2] Desktop agent dictates billable hours: total_seconds is client-supplied, unbounded, and never reconciled against wall clock
- **Category:** abuse | **File:** app/Http/Controllers/Api/Desktop/SessionController.php | **Line:** 145, 161 (validated in app/Http/Requests/Desktop/HeartbeatRequest.php:17 and StopSessionRequest.php:18)
- **Impact:** This is the product's core integrity guarantee and it does not exist. Any employee with their own desktop token (which sits in plaintext on their own machine) can `curl -X POST /api/desktop/sessions/{id}/stop -d 'total_seconds=360000&stopped_at=...'` and mint 100 billable hours from a session that ran for 4 seconds. `syncWorkHour` writes the value straight into `work_hours` (`hours = total_seconds/3600`), which is what Reports, Timeline, the dashboard and any invoicing read. There is no server-side cap, no comparison against `started_at`/`stopped_at`, no comparison against the count of activity samples or screenshots, and no anomaly flag. Grepping every use of `total_seconds` in app/ turns up exactly one sanity cap — TeamController.php:95 `min($overlap, 16 * 3600)` — and it only applies to the live Team view for sessions that straddle a day boundary; the persisted WorkHour row keeps the raw number. For an agency selling this to enterprises to *prevent* time fraud, a customer's first forensic audit ends the contract.
- **Fix:** Make the clock server-authoritative; never derive a cap from a client-supplied timestamp.

1. Add a server anchor. On `TrackingSession` create, stamp `server_started_at = now()` (server clock, not `$data['started_at']`) and keep a server-side `server_last_seen_at` updated on every heartbeat. Keep the client `started_at` only as a display value, and bound it in `StartSessionRequest`: `['required','date','before_or_equal:now','after:'.now()->subDay()]` so an offline-queued start is still supported but a 1999 backdate is not. Bound `stopped_at` in `StopSessionRequest` the same way (`before_or_equal:now` plus `after_or_equal:started_at`).

2. Clamp increases only, against the server anchor, in both `heartbeat()` (SessionController.php:144) and `stop()` (:159):
   $ceiling = $session->server_started_at->diffInSeconds(now()) + $grace;   // $grace ≈ 2 × heartbeat interval
   $incoming = min((int) $data['total_seconds'], $ceiling);
   if ($incoming > $session->total_seconds) {
       $step = now()->diffInSeconds($session->server_last_seen_at);          // server-measured, NOT $data['heartbeat_at']
       $incoming = min($incoming, $session->total_seconds + $step + $grace);
   }
   Do NOT reject decreases — `MonitoringController.php:270` and idle deduction legitimately lower the value.

3. Gate `stop()` on status, mirroring the existing check at SessionController.php:135: abort (409) if `$session->status !== STATUS_ACTIVE`, so a finished session's `work_hours` rows can't be rewritten by replaying the stop call.

4. Keep `'max:'.(24*3600)` on both form requests as a cheap floor-level guard — redundant once (2) lands, but useful defence in depth.

5. Cross-check as an *anomaly flag*, not a hard cap. Comparing to `tracking_activity_samples` count × interval must not gate the write — activity tracking is entitlement-gated (`routes/api.php:64`) and batches arrive late, so a hard cap would delete real hours. Instead, whenever the raw claimed value exceeded the clamped value, write an audit row (there is already a `tracking_audit_logs`-style pattern in MonitoringController) and surface it on the Team/Timeline views so an admin sees tampering.

6. Since the flaw shipped, add a read-only detection query for existing data: sessions where `total_seconds` exceeds `TIMESTAMPDIFF(SECOND, started_at, COALESCE(stopped_at, last_heartbeat_at)) + grace`, so pre-fix rows can be reviewed before any invoice is trusted. Do not auto-rewrite historical `work_hours`.

### [high-3] TrustProxies is unconfigured — every IP-keyed rate limiter collapses into one global bucket behind a proxy/CDN
- **Category:** abuse | **File:** app/Http/Middleware/TrustProxies.php | **Line:** 14-15
- **Impact:** The deployment target is a Hostinger VPS that also fronts other sites; if any reverse proxy, load balancer or Cloudflare sits in front (the norm for a public SaaS), `$request->ip()` returns the proxy's address for every visitor. Every IP-keyed throttle then becomes a single shared bucket: one attacker consumes the 60/min api budget and the 6/min contact budget for the entire internet (trivial denial of service on signup, contact, password reset and the desktop API), and the login limiter degenerates to per-email-only. Conversely, if the proxy is later configured to pass X-Forwarded-For without this being set, the limits silently key on an untrusted attacker-supplied header.
- **Fix:** The claim's proposed fix is dangerous as written and its diagnosis is incomplete. Correct remediation, in order:

**1. Do NOT blindly set `protected $proxies = '*';`.** `'*'` makes Laravel trust the *immediate* peer and honour whatever `X-Forwarded-For` it sends. If PHP-FPM is ever reachable directly (Hostinger VPS 2.24.11.90 also fronts staffvora.com and gymrun.tech per the deploy notes, so origin-direct traffic is plausible), `'*'` hands every attacker a one-header bypass of *every* rate limit — strictly worse than today. Pin the actual edge: if Cloudflare, `protected $proxies = [...Cloudflare IPv4/IPv6 CIDRs...]` (or a `TRUSTED_PROXIES` env read), plus lock nginx/Apache to accept :443 only from those ranges. If there is no proxy, leave `$proxies` null — that is already correct.

**2. Fix the real, unconditional amplifier the claim missed — `app/Providers/RouteServiceProvider.php:28`.**
`return Limit::perMinute(60)->by($request->user()?->id ?: $request->ip());`
`$request->user()` with no guard argument resolves the **default** guard, which is `'web'` (session) per `config/auth.php:20`. The `api` middleware group (`app/Http/Kernel.php:71-75`) has no `StartSession` and `EnsureFrontendRequestsAreStateful` is commented out, so a Sanctum bearer-token request has no session and `$request->user()` returns **null**. Every authenticated desktop API call is therefore already keyed by IP, with or without a proxy. Change to `$request->user('sanctum')?->id ?: $request->ip()` — or better, key on the token id — and raise/segment the limit for the desktop group.

**3. Give the desktop API its own limiter.** 60/min shared across an office is nonsense for this traffic shape. Register e.g. `RateLimiter::for('desktop', fn ($r) => Limit::perMinute(120)->by($r->user('sanctum')?->id ?: $r->ip()))` and apply `throttle:desktop` to the `Route::prefix('desktop')` group in `routes/api.php`, keeping `throttle:api` strict for the unauthenticated `/api/desktop/login` and `/api/slack/interact` paths only.

**4. Keep the email component in the auth limiters.** `LoginRequest.php:96` and `PasswordResetCodeController.php:33,82` already include the email in the key, so they degrade to per-email rather than failing open — do not "fix" them by removing the IP; add a second, coarser per-IP limiter once the IP is trustworthy.

**5. Verify after deploy** that `$request->ip()` logs real client addresses, and that `X-Forwarded-Proto` is honoured — there is no `URL::forceScheme('https')` anywhere in `app/` or `config/`, so with TLS terminated at a proxy and no trusted proxies, Laravel will generate `http://` URLs and break signed URLs, redirects and secure-cookie behaviour. That side effect is arguably a bigger operational hazard than the throttling and the claim does not mention it.

### [high-4] Employees can fabricate unlimited billable hours: total_seconds is self-reported and unbounded on the desktop API
- **Category:** abuse | **File:** app/Http/Requests/Desktop/StopSessionRequest.php | **Line:** 18 (and HeartbeatRequest.php:17); app/Services/TrackingSessionService.php:87-90
- **Impact:** There is no upper bound and no reconciliation against started_at/stopped_at wall-clock. Any employee holding a desktop token (every tracked user has one) can `POST /api/desktop/sessions/{id}/stop` with `total_seconds=99999999` and have those hours mirrored straight into work_hours, which drives the Work Hours Report, payroll/client exports, Slack digests and the dashboard. For a product whose entire value is trustworthy billable time, this makes the numbers unauditable. The UI-side 16h cap in TimeEntryController::summaryStatsFor:336 only affects display of live sessions, never the stored value.
- **Fix:** The proposed fix is directionally right but incomplete in three ways:

1. `started_at` is ALSO fully client-controlled and unbounded — `app/Http/Requests/Desktop/StartSessionRequest.php:18` is just `'started_at' => ['required', 'date'],`, and `SessionController::start:56` stores it via `BusinessTime::fromClient($data['started_at']) ?? now()` (which silently falls back on a parse failure). So clamping `total_seconds` to `started_at->diffInSeconds($stoppedAt)` is trivially bypassed by backdating `started_at` a week. Any clamp must be anchored to SERVER-observed time: bound `started_at` and `stopped_at` to a sane window around `now()` (e.g. reject more than a few minutes in the future or more than N hours in the past — offline queue tolerance), and persist a server-set `received_at` as the authoritative anchor for reconciliation.

2. The heartbeat path needs a monotonicity rule, not just a ceiling. `SessionController::heartbeat:144-148` lets `total_seconds` move arbitrarily UP or DOWN — the down direction is a time-erasure vector, and inflated heartbeat totals reach `work_hours` even without a stop call, because `TrackingSessionService::finalize:38-46` (used by the single-device takeover at `SessionController.php:72-81` and by the stale-session sweep) sets `stopped_at = last_heartbeat_at` and calls `syncWorkHour`. Rule: `new_total <= previous_total + (server_now - last_heartbeat_at) + skew`, and never allow a decrease except through an admin action.

3. An absolute 24h/session ceiling is near-useless alone, since an attacker can just open N sessions. The durable control is elapsed-server-time reconciliation plus corroboration against the evidence tables — `tracking_screenshots` / `tracking_activity_samples` counts × the configured sample interval should bracket the claimed seconds; flag sessions whose claimed time materially exceeds what the captured evidence supports.

Additionally, and not mentioned by the claim: wrap `SessionController::stop:159-168` in a DB transaction. Today the session update commits before `syncWorkHour` runs, so a `work_hours.hours` decimal(5,2) overflow (or any other failure) leaves `tracking_sessions` inflated with no matching `work_hours` row — permanently divergent numbers between the Timeline and the Work Hours report. Widening that column without first adding the clamp would remove the accidental brake and make the fabrication fully silent.

Also worth raising as a separate defect found on the same path: `StartSessionRequest.php:19-20` uses `'exists:clients,id'` and `'exists:upwork_profiles,id'` with no organization scoping, so the existence check consults rows across all tenants.

### [high-5] Client-controlled session timestamps are unbounded, letting one request spin a per-day loop and mass-create work_hours rows
- **Category:** abuse | **File:** app/Services/TrackingSessionService.php | **Line:** 105-131 (inputs from app/Http/Requests/Desktop/StartSessionRequest.php:15 and StopSessionRequest.php:17)
- **Impact:** `BusinessTime::fromClient()` applies no clamping, so an agent can start a session at `1970-01-01` and stop it at `2100-01-01`. `dailySeconds()` then iterates ~47,000 Carbon day-steps inside the request, and with a large enough `total_seconds` each day clears the `>= 1` guard, so `syncWorkHour` issues tens of thousands of individual `WorkHour::create()` INSERTs — one HTTP request that pins a worker and floods the tenant's reporting table with junk rows that appear in every date-filtered report thereafter. Even without malice, a desktop machine with a badly wrong system clock (the realistic case) files hours on the wrong year. Note the same unbounded value reaches attendance: SessionController::ensureClockedIn() at line 116-125 derives `action_date` straight from the client's `started_at`, which is exactly the action_date mis-filing class of bug.
- **Fix:** The proposed fix is directionally right but incomplete in three ways and wrong in one.

WRONG: `'stopped_at' => [... 'after:started_at']` cannot work as written — `started_at` is not in the stop payload (StopSessionRequest has only stopped_at/total_seconds/activity_percent/task_note); the start time lives on the route-bound `TrackingSession`. The span check must be done against `$this->route('session')->started_at` (in the FormRequest via a closure rule or `withValidator`), not against a sibling field.

MISSED #1 — the heartbeat is the same hole, and it bypasses the proposed fix entirely. `app/Http/Requests/Desktop/HeartbeatRequest.php:19` is `'heartbeat_at' => ['nullable', 'date'],` — also unbounded — and it writes `last_heartbeat_at` (SessionController.php:147). `dailySeconds()` line 104 reads `$end = $session->stopped_at ?? $session->last_heartbeat_at ?? $start;`, and `CloseStaleTrackingSessions.php:39-50` calls `finalize($session, $session->last_heartbeat_at ?? $session->started_at)`. So bounding only start/stop leaves the identical loop reachable via heartbeat + the stale sweep — and there it detonates inside the scheduler, taking down the cron for every tenant rather than one request. Bound `heartbeat_at` too.

MISSED #2 — `total_seconds` has no `max` in either StopSessionRequest.php:18 or HeartbeatRequest.php:17. Independent of the date span, a single stop can claim 10,000 hours of work on one legitimate day. Add a ceiling tied to the session's real elapsed span (e.g. `min(elapsed_seconds * 1.05, 24h)`) — this is the actual timesheet-fraud primitive and it survives every date fix.

MISSED #3 — `SessionController::stop()` (line 153) has no state guard, unlike `heartbeat()` which returns 409 when `$session->status !== STATUS_ACTIVE` (lines 135-140). The same session can be re-stopped indefinitely, re-running the delete+reinsert loop each time. Add the same status check to `stop()`.

Also refine the two guards the auditor did propose:
- Prefer CLAMP over REJECT at the boundary. The code deliberately trusts the desktop clock for offline-queued starts (comment at SessionController.php:101-104), so a hard `after:-7 days` 422 means a user with a skewed clock cannot track at all. Validate a generous window (e.g. started_at within -7d..+1d, stopped_at within started_at..+24h) but have `BusinessTime::fromClient()` gain a `clampToWindow()` sibling that pins out-of-window values to `now()` and logs, so skew degrades gracefully instead of breaking tracking.
- In `dailySeconds()`, cap iterations hard (bail past ~31 days, log, and fall back to `[$start->toDateString() => $total]`) — correct as proposed — but ALSO fix the write pattern: replace the N × `WorkHour::create()` at TrackingSessionService.php:87 with a chunked `WorkHour::insert()` (manually stamping `organization_id` + timestamps, since `insert()` skips the `creating` hook in BelongsToOrganization), and wrap the delete+insert in a `DB::transaction` so a partial flood cannot survive a timeout. Even a legitimate 3-day overnight session is currently 3 separate round-trips with no atomicity.

### [high-6] Desktop login API has no brute-force protection — bypasses the web login's 5-attempt lockout
- **Category:** authz | **File:** app/Http/Controllers/Api/Desktop/AuthController.php | **Line:** 18-32; routes/api.php:39
- **Impact:** The web login is protected per-account (LoginRequest.php:75 — 5 attempts keyed by email+IP), but the desktop API authenticates the exact same credentials with only a generic 60-requests/minute-per-IP bucket and NO per-account counter and NO lockout. An attacker gets 60 guesses/minute against any known account, 86,400/day from one IP and unlimited by rotating IPs — and a success mints a Sanctum token that never expires (config/sanctum.php:52 `'expiration' => null`), so revocation depends on an admin deactivating the user. With `config/cors.php` set to `'paths' => ['api/*'], 'allowed_origins' => ['*']`, the attack can also be fanned out through third-party website visitors' browsers.
- **Fix:** The proposed fix is directionally right but incomplete in one place and operationally risky in another.

1) MUST ADD (missing from the claim, and the highest-value change): enforce the user's own active flag in the desktop login, at parity with LoginRequest.php:56. In AuthController::login, immediately after the Hash::check block and before OrganizationAccess::denialFor, add `if (! $user->isActive()) { return response()->json(['message' => 'Your account has been deactivated. Please contact your administrator.', 'code' => 'account_deactivated'], 403); }`. Without this, UserController.php:683's token revocation is cosmetic — the deactivated user re-mints a token on the next request. Better still, move the check into App\Support\OrganizationAccess::denialFor($user) as the first condition (before the `! $user->organization_id` early return at :23), so the web app, the desktop login, and EnsureOrganizationIsUsable (which runs on every authenticated desktop request) all inherit it from one place — that also kills any *existing* token the moment the flag flips, closing the window between deactivation and token cleanup.

2) THROTTLE — use two limiters, not one. An `email|ip` key alone (what the claim proposes, and what LoginRequest.php:96 already does) is defeated by IP rotation, which config/cors.php's wildcard makes free. Register in RouteServiceProvider::boot: `RateLimiter::for('desktop-login', fn ($r) => [Limit::perMinute(5)->by(Str::lower((string) $r->input('email')).'|'.$r->ip()), Limit::perMinutes(60, 10)->by(Str::lower((string) $r->input('email'))), Limit::perMinute(20)->by($r->ip())]);` and attach `->middleware('throttle:desktop-login')` to routes/api.php:39. The email-only bucket is the one that actually stops distributed stuffing. Apply the same email-only bucket to the web LoginRequest throttleKey — it has the identical rotation weakness. Also make the failure path constant-time (`Hash::check($data['password'], $user?->password ?? Hash::make('invalid'))` or call `Hash::check` against a dummy hash when `$user` is null) to close the enumeration timing oracle at AuthController.php:28.

3) SANCTUM EXPIRATION — do NOT just set `'expiration' => 43200` as written. This is a long-running desktop time tracker; a hard expiry with no refresh endpoint will log clients out mid-shift and lose in-flight tracking data — a production regression worse than the risk it mitigates. Sequence it: first ship the isActive check in (1) (which gives immediate, admin-controlled revocation of live tokens), plus a scheduled prune of tokens whose `personal_access_tokens.last_used_at` is older than N days, and only then introduce a finite `expiration` once the desktop client has a silent refresh path.

4) CORS — narrowing is correct and cheap here. The desktop client is a native app and is not subject to CORS at all, and /api/slack/interact is server-to-server from Slack, so nothing legitimate needs a browser origin on `api/*`. Set `'allowed_origins' => []` (or just your own app hosts) in config/cors.php:22 rather than merely "narrowing" — verify first with a grep that the Inertia/React front end makes no `fetch('/api/...')` calls, since the SPA rides web routes.

5) Add a `Illuminate\Auth\Events\Failed`/Lockout listener that logs desktop-login failures with email+IP; today a sustained credential-stuffing run against this endpoint leaves no trace anywhere.

### [high-7] Deactivating an employee does not lock them out — the desktop login endpoint skips the is_active check that web login enforces
- **Category:** authz | **File:** app/Http/Controllers/Api/Desktop/AuthController.php | **Line:** 26-46
- **Impact:** UserController::setStatus (line 682-684) and bulkStatus (line 733-735) both do `$user->tokens()->delete(); // revoke desktop access immediately`, and web login blocks deactivated accounts (app/Http/Requests/Auth/LoginRequest.php:56-64: `if (! Auth::user()->isActive()) { Auth::logout(); ... }`). The desktop login has neither check — `OrganizationAccess::denialFor()` (app/Support/OrganizationAccess.php:22-56) only inspects the *organization's* status and subscription, never `users.is_active`. So a fired employee whose account was just deactivated simply reopens the desktop app, re-enters the password they still know, gets a brand-new Sanctum token, and resumes logging billable hours, clocking in, and uploading screenshots. The revocation is theatre. This is the single most likely real-world abuse of the product because it needs no tooling at all.
- **Fix:** Put the gate in ONE place, but above the legacy escape hatch, and handle the web guard separately.

1) app/Support/OrganizationAccess.php — insert the check at the TOP of denialFor(), BEFORE the `if (! $user->organization_id) { return null; }` early-return at lines 23-25. If it goes after (as the original fix implies), every legacy/null-org user still bypasses it:

    public static function denialFor(User $user): ?array
    {
        if (! $user->isActive()) {
            return [
                'code' => 'account_deactivated',
                'message' => 'Your account has been deactivated. Please contact your administrator.',
                'status' => 403,
            ];
        }

        if (! $user->organization_id) { return null; }
        ...

   Use `$user->isActive()` (User.php:156-159, null-safe `?? true`), not `$user->is_active`, so pre-column rows stay usable.

   This single edit covers both holes at once: AuthController::login already calls denialFor() at line 34, so no new code is needed in the desktop controller; and `tenant.usable` on the desktop route group (routes/api.php:41) then rejects ALREADY-ISSUED tokens on every request, closing the race where a token minted just before deactivation outlives it. Note `desktop.logout` is in EnsureOrganizationIsUsable::ALWAYS_AVAILABLE_ROUTES (line 21) — leave it there; letting a deactivated client clear its own token is desirable.

2) app/Http/Middleware/EnsureOrganizationIsUsable.php — the non-JSON branch at line 51 does `return redirect()->route('billing.index')`. For `account_deactivated` that is wrong: it hands a fired employee the billing page and, because billing.*/profile.*/password.* are in ALWAYS_AVAILABLE_ROUTES (lines 15-22), leaves those routes reachable. Special-case it: `if ($denial['code'] === 'account_deactivated') { Auth::guard('web')->logout(); $request->session()->invalidate(); $request->session()->regenerateToken(); return redirect()->route('login')->withErrors(['email' => $denial['message']]); }` — and drop profile.*/password.* out of the always-available list for this code, or check the deactivation before the ALWAYS_AVAILABLE_ROUTES short-circuit at line 26.

3) Kill live browser sessions on deactivation. config/session.php:21 uses the `file` driver and app/Http/Kernel.php:58-69 omits Illuminate\Session\Middleware\AuthenticateSession, so UserController::setStatus (line 682-684) and bulkStatus (line 734-736) — which delete Sanctum tokens only — leave an open Inertia session fully working until it expires. Either move SESSION_DRIVER to `database` and delete the user's session rows alongside the tokens, or rely on step 2 (the middleware runs on every web request, so an active session gets logged out on its next request). Step 2 is the cheap correct answer; do not ship step 1 without it.

4) Optional hardening on AuthController::login itself: it has no login-specific throttle beyond the `api` group's ThrottleRequests::class.':api' (Kernel.php:73) and, unlike LoginRequest (which hits the RateLimiter at lines 46 and 58), records nothing per-email. Add `->middleware('throttle:5,1')` to routes/api.php:39 so the desktop endpoint isn't a softer password-spray surface than the web form.

5) Regression test worth adding: deactivate a user, then POST /api/desktop/login with correct credentials and assert 403 + code `account_deactivated`; and separately, mint a token, deactivate, then hit /api/desktop/sessions/start with the old token and assert 403.

### [high-8] Password reset codes are delivered through the platform's Slack bot and a single global fallback channel, never the tenant's
- **Category:** data-exposure | **File:** app/Http/Controllers/Auth/PasswordResetCodeController.php | **Line:** 63-67 (token resolution app/Services/SlackBotService.php:25-34)
- **Impact:** The reset flow runs before authentication, so no tenant is bound and the per-org Slack token is never reachable. Result: (a) a plaintext account-takeover credential for customer A's employee — 6-digit code, plus their full name and email — is posted into the single SLACK_RESETS_CHANNEL, a channel owned by the platform operator (or by whoever set that env var), completely outside the customer's control and visible to everyone in that channel; and (b) every workspace that connected its own Slack bot under Settings > Slack gets no reset DMs at all, because token() silently falls back to the platform token, which is not a member of their workspace. The code has a 10-minute TTL and 5 verify attempts, so anyone reading that channel can take over the account outright.
